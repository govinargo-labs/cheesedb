    Deleting the bad source isn’t enough.
    
    
    An agent builds memory from sources it can’t fully trust. When one turns out to be bad, everything the agent learned from it is still in memory, and the agent keeps acting on it.
    
    
    
      
    
        
        
    Wrong
    
        
    A tool returned bad data, and three memories were built on it.
    
      
    
      
    
        
        
    Malicious
    
        
    A web page planted false facts or instructions: memory poisoning and prompt injection.
    
      
    
      
    
        
        
    Private
    
        
    A user asked for their data to be deleted, including what the agent concluded from it.
    
      
    
    
    
  
    

  
    
    
    Every record has three parts.
    
    
    Erase has to remove text without losing history, so each record is split in a way that keeps the history.
    
    
    
      
    
        
    Header
    The record’s id and a hash that seals it to the record before it. Never erased, so the chain stays verifiable.
    
        
    Structure
    What kind of record it is and which sources it depends on. Never erased, so recall still works after an erase.
    
        
    Content
    The text itself, with a random salt. The only part erase removes.
    
      
    
      
    
    
  
    

  
    
    
    A few lines of Go.
    
    
    This is the same story as the demo above.
    
    
    
      

    s, err := cheesedb.Open("/data/cheesedb")   // a folder you choose, created 0700
tok, err := s.CreateAgent("alice")          // Alice's token, shown once: keep it safe
alice, err := s.OpenAgent(tok)              // the only way to reach Alice's data
defer alice.Close()

a, _ := alice.AddLot("user_message", []byte("I live in Pune"))
b, _ := alice.AddLot("web_page", []byte("profile: lives in Pune"))
c, _ := alice.AddLot("weather_tool", []byte("Pune: rain"))

m1, _ := alice.Remember([]byte("user lives in Pune"), cheesedb.Leg{a}, cheesedb.Leg{b}) // from A, or from B
m2, _ := alice.Remember([]byte("Pune is rainy"), cheesedb.Leg{c})
m3, _ := alice.Remember([]byte("carry an umbrella"), cheesedb.Leg{m1, m2})             // needs M1 and M2

removed, _ := alice.Recall(c, cheesedb.Fair, cheesedb.Untrusted) // the weather tool was wrong
// removed == [m2, m3]; m1 survives because it does not depend on C
    
    
    
    
    Install the command-line tool with go install github.com/govinargo-labs/cheesedb/cmd/cheesedb@latest. It has one command per feature, including cheesedb find, which searches the raw bytes of the files to prove erased text is gone. Needs Go 1.26.5 or newer. Developed on macOS and tested on Linux in CI. Windows isn’t supported yet.

    When to use it, and when not to.
    
    
    
      
    
        
    Use CheeseDB when
    
        
      
          
    • Your agents learn from sources you can’t fully trust.
      • 
          
    • You need to remove a source and everything declared to depend on it, however deep the chain goes.
      • 
          
    • Erased text must really be gone from the files.
      • 
          
    • You want each agent isolated by design, not by a filter in your code.
      • 
          
    • You want an embedded Go library with no server and no dependencies.
      • 
        
    
      
    
      
    
        
    Use something else when
    
        
      
          
    • You need queries or search. CheeseDB looks up by id only, so keep search in your vector store and check each result against CheeseDB.
      • 
          
    • Startup time matters with very long histories: about 0.7 s at 1M memories. Snapshots are planned.
      • 
          
    • An agent’s memory graph won’t fit in RAM: about 205 bytes per memory.
      • 
          
    • You need production guarantees today. This is a preview.
      •

    Read this before you rely on it.
    
    
    
      
    
      
    
        
    Preview v0.1.0: not independently security reviewed.
    
        
      
          
    • The API and on-disk format may change before v1.0.
      • 
          
    • Tamper-evident, not tamper-proof. Anyone who can write the files can rebuild the hash chain. Keep the head fingerprint that Verify() returns somewhere else and compare it later.
      • 
          
    • Isolation stops mistakes and prompt injection, not the host program. Whoever holds the store or the folder can read every agent’s files.
      • 
          
    • Legs are declared by the caller. If a memory was really learned from a source but no leg says so, recalling that source won’t remove it.
      • 
          
    • Only Erase removes text from disk. Untrusted hides memories until you run Compact(). Backups and copies keep their data.
      • 
          
    • Damage near the end of an active log is cut off and reported in Report.DroppedBytes, so check it after opening.
      • 
        
    
        
    The full list is in the README and the threat model.
    
      
    
    
    
  
    

  
    
    
    Why cheese?
    
    
    
      
      
    
        
    “Lot” and “recall” are food-safety words. A cheese maker records which lots of milk went into which wheels, so when one lot turns out to be contaminated, they recall exactly the cheese made from it.
    
        
    CheeseDB does the same for what an agent remembers. The name also nods to the Swiss cheese model of safety: stack several layers of protection, and harm only happens when the holes in every layer line up.
