How it scales.

One agent with a search index (768 values per memory), from a thousand memories to a million. These are CheeseDB’s own times: the embedding model is not included. With a local one, turning a question into a vector took 17 ms.

Median of 3 runs on an Apple M1 Max. In memory each vector takes one byte per value; the few rows that could make the top results are re-checked with the exact values on disk, so results are exact. The command and the MCP server open the store for every call, so each search reloads the index; they suit agents of up to about 100,000 memories. A Go program that keeps the store open loads it once. With real embeddings and varied text at 1M, search still ranked the right memories first among a million look-alikes, and none came back after their source was recalled. Models, measured apart: embedding one question 17 ms; embedding a million memories about 36 minutes (CheeseDB’s part: 42 s). Method and every number: BENCHMARKS.md.

Median of 3 runs on an Apple M1 Max (macOS, internal SSD), SQLite 3.53, PostgreSQL 17 and Neo4j Community 2026.10. PostgreSQL and Neo4j ran over TCP on localhost. Writes are close because the disk flush dominates for every engine. SQLite is smaller on disk and starts far faster. ¹ A new connection to a server that is already running; booting the Neo4j server took 6.5 to 8.2 s. The Neo4j model and queries are ours, and an expert may do better. These numbers are for the library without a search index. Method and caveats are in BENCHMARKS.md.
